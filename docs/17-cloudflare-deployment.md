## 1. Purpose

This document defines how the Ultimate Fleet GPS website will be built, previewed, validated, deployed, connected to its production domain, monitored, and rolled back on Cloudflare Pages.

It governs:

- Cloudflare account and project ownership;
- GitHub integration;
- production and preview branch behavior;
- build settings and environment variables;
- custom domains, DNS, TLS, and canonical hosts;
- redirect and response-header deployment;
- preview indexation and access controls;
- static asset and cache behavior;
- form-backend boundaries;
- analytics and monitoring activation;
- launch and migration procedures;
- deployment verification;
- rollback and incident response; and
- operational access and maintenance.

This plan implements the static-export architecture in `16-technical-architecture.md`. It does not authorize publishing unverified business information, job terms, services, locations, or entity relationships.

## 2. Deployment Outcome

The deployment system is successful when:

- approved commits produce reproducible static builds;
- every pull request or approved working branch can receive a safe preview;
- only `main` deploys to the production environment;
- the canonical domain serves the intended release over HTTPS;
- the alternate host and verified legacy URLs redirect correctly;
- preview domains remain out of search indexes;
- forms use the correct environment and never expose secrets;
- production analytics does not collect preview traffic;
- failed builds do not replace the working production deployment;
- a known-good release can be restored quickly; and
- Ultimate Fleet GPS retains durable control of the Cloudflare account, domain, DNS, and production project.

## 3. Hosting Model

### Approved baseline

Use Cloudflare Pages to host the `out` directory generated by a Next.js static export.

```text
GitHub repository
    -> Cloudflare Pages build
    -> npm clean install
    -> project validation
    -> next build
    -> out/ static artifact
    -> Cloudflare global edge delivery
```

### Trusted backend boundary

Cloudflare Pages serves public HTML, CSS, JavaScript, images, fonts, sitemaps, robots directives, headers, and redirects. It must not expose or perform secret-dependent operations in browser code.

Use a separately configured Cloudflare Worker, a reviewed Pages Function, an approved ATS form, or another approved server-side integration for:

- application submissions;
- installer-network registrations;
- candidate referrals;
- commercial inquiries;
- Turnstile server validation;
- ATS and CRM credentials;
- resume or file transfer;
- signed webhook requests;
- server-confirmed conversion events; and
- durable queues or retries.

The exact form and integration platform remains a project decision blocker.

## 10. Build Configuration

### Recommended Pages settings

| Setting | Required value |
|---|---|
| Framework preset | Next.js Static HTML Export |
| Production branch | `main` |
| Build command | `npm run build` |
| Build output directory | `out` |
| Root directory | `/` unless the repository becomes a monorepo |
| Package manager | npm unless changed by decision |
| Dependency install | Determined from committed `package-lock.json` |
| Node version | Project-pinned supported version |

### Build command contract

`npm run build` must:

1. exit nonzero on a fatal validation failure;
2. produce a Next.js static export;
3. place deployable files in `out/`;
4. include `_headers` and `_redirects` when used;
5. exclude draft, blocked, and test content;
6. exclude expired active-job schema and sitemap entries;
7. generate correct environment-specific metadata; and
8. avoid network dependencies that make ordinary builds fragile unless explicitly approved.

### Quality-gate approach

Two supported patterns exist:

**Pattern A: validate inside the Pages build**

```text
npm run check
```

Where `check` performs type checking, linting, tests, content validation, schema validation, link validation, and the production build.

**Pattern B: GitHub checks plus Pages build**

- GitHub Actions runs the complete quality suite.
- Cloudflare runs `npm run build`.
- GitHub branch protection requires quality checks before merge, where branch protection is configured and pull requests are used.

Pattern B avoids repeating every expensive test in Cloudflare, but Cloudflare must still fail on build-time content and route errors. Select one documented production gate and keep local, GitHub, and Cloudflare Node/dependency versions aligned.

### Static site rule

The exported site has no safe browser-side secret. Any value bundled into HTML or JavaScript must be treated as public.

### Private values belong elsewhere

Store these only in the trusted Worker, Function, ATS, CRM, or integration environment:

- Turnstile secret key;
- ATS credential;
- CRM credential;
- webhook signing secret;
- email/SMS API key;
- private storage credential;
- server-side analytics secret;
- error-monitoring write token; and
- authentication or encryption key.

### Secret governance

- use Cloudflare encrypted secrets or the approved provider's secret store;
- separate preview and production secrets;
- grant least privilege;
- never echo secrets in build or runtime logs;
- never commit real secrets;
- maintain rotation ownership and schedule;
- rotate immediately after suspected exposure;
- remove vendor access and rotate affected credentials after offboarding; and
- keep `.env.example` limited to names and safe descriptions.

### Build-time private data

Avoid fetching protected candidate, customer, or operational data during a public static build. If a private content API is later introduced, ensure secrets are available only at build time, excluded from output, not logged, and limited to public-approved content.

## 17. Preview Indexation Protection

Use layered protection.

### Layer 1: Response header

Apply `X-Robots-Tag: noindex, nofollow` to the Pages project hostname and preview aliases through a verified `_headers` rule or an equivalent Cloudflare configuration.

Example pattern requiring replacement with the actual project hostname and live verification:

```text
https://ultimate-fleet-gps-site.pages.dev/*
  X-Robots-Tag: noindex, nofollow
```

Branch and deployment host patterns must also be tested. Do not assume one host rule covers every generated preview URL.

### Layer 2: Metadata

Preview builds may also output `noindex, nofollow` metadata as defense in depth. Response headers remain preferable for an environment-wide control.

### Layer 3: Access control

Use Cloudflare Access or another approved restriction for stakeholder previews containing sensitive or unapproved information. Access control protects confidentiality; `noindex` protects discovery. They serve different purposes.

### Layer 4: Operational controls

- do not link previews from public pages;
- do not submit previews to search engines;
- do not use preview URLs in job-board listings, profiles, social bios, citations, or permanent documents;
- remove obsolete branch aliases where appropriate; and
- audit indexed `pages.dev` URLs after launch.

### Production `pages.dev` hostname

The default production Pages hostname can also become discoverable. The approved handling, set 2026-10-26, is both layers:

- keep the hostname-scoped `noindex` rule in `public/_headers` permanently, with canonical references to the custom domain; and
- at launch, 301 only the production project hostname to the canonical custom domain with a Cloudflare Bulk Redirect.

Do not redirect all wildcard preview hostnames to production, because that would destroy preview behavior and could publish unapproved paths indirectly.

### pages.dev indexing

`https://ultimate-fleet-gps-site.pages.dev/` is the temporary build domain. The live domain will be `https://ultimatefleetgps.net/`. Handle the two phases differently.

**Before launch**

- The pages.dev build domain must not be indexed.
- Use a hostname-scoped `X-Robots-Tag: noindex` rule in `public/_headers` that targets only the pages.dev hostnames. Never use a bare `/*` rule, because `public/_headers` applies to every host serving the build, including production.
- Per the Cloudflare Pages Headers documentation, a rule scoped to a host puts the full `https` URL on the first line, and hostname placeholders (`:name`) are allowed. Placeholders stop at a period. Example pattern, to be verified against the live documentation before use:

```text
https://ultimate-fleet-gps-site.pages.dev/*
  X-Robots-Tag: noindex

https://:version.ultimate-fleet-gps-site.pages.dev/*
  X-Robots-Tag: noindex
```

- Canonical URLs already point to `https://ultimatefleetgps.net/`, which does not resolve until the custom domain is attached. Canonicals alone do not prevent indexing of the build domain.

**At launch**

- Keep both `noindex` rules in `public/_headers`. Do not remove the production pages.dev rule.
- Add a Cloudflare Bulk Redirect in the dashboard that 301s the production pages.dev hostname to `https://ultimatefleetgps.net/`. Cloudflare's page for this case, "Redirecting *.pages.dev to a Custom Domain" (https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/), uses a Bulk Redirect list with the `<project>.pages.dev` hostname as the source, a 301 status, and the options Preserve query string, Subpath matching, Preserve path suffix, and Include subdomains. No Pages Functions are needed.
- A zone Redirect Rule matching a pages.dev host was not confirmed in the Cloudflare documentation. The pages.dev hostname is not in the project's zone, so use Bulk Redirects unless Cloudflare documents otherwise.
- Redirect only that hostname. Never redirect preview wildcard hosts, which keep the `noindex` rule.

**Precedence.** Cloudflare documents that redirects run before headers (https://developers.cloudflare.com/pages/configuration/redirects/). While the Bulk Redirect is active, the production pages.dev `noindex` rule never reaches a visitor, because the redirect wins. The rule stays as a permanent fallback for when the redirect is removed or fails. Preview hostnames are never redirected, so their `noindex` rule always applies.

### Deployment assumptions (2026-10-26)

- The site is a Next.js static export (`output: "export"`, `trailingSlash: true`). There are no Pages Functions or Workers.
- `public/_headers` is the only header and redirect file in the build. There is no `_redirects` file, and `_redirects` cannot redirect by hostname.
- Host-level redirects (production pages.dev to the apex, `www` to the apex, and HTTP to HTTPS) are dashboard settings, not repository files.
- The apex, `https://ultimatefleetgps.net/`, is the canonical host. All canonicals, `og:url`, sitemap URLs, `robots.txt` and schema URLs derive from `business.url` (`NEXT_PUBLIC_SITE_URL`, defaulting to the apex). Do not set that variable to a pages.dev URL.
- The sitemap omits `lastmod` until real content-change dates are available.
- `npm run build` runs `scripts/validation/check-build-output.mjs` afterward. It fails on a relative or off-domain canonical, and on "pages.dev" anywhere in `out/` outside `_headers`.

## 22. Redirect Deployment

### Repository location

For static Pages deployment, store the source file at:

```text
public/_redirects
```

Next.js copies it into the final static output. The build must confirm:

```text
out/_redirects
```

exists and matches the approved redirect registry.

### Syntax

Cloudflare Pages uses one rule per line:

```text
[source] [destination] [status]
```

Example:

```text
/contact-us /contact/ 301
/career-opportunities /careers/ 301
```

### Redirect requirements

- use an explicit status code;
- place static rules before dynamic rules;
- keep specific rules before broad patterns;
- avoid chains and loops;
- use one canonical trailing-slash format;
- do not redirect arbitrary missing routes to the homepage;
- do not use redirects to mask thin duplicate pages;
- test every known legacy route; and
- preserve safe campaign parameters only where platform behavior is confirmed.

### Platform limits

Cloudflare currently documents limits for `_redirects`, including separate static and dynamic rule counts. If the migration exceeds those limits, use Bulk Redirects or another approved zone-level mechanism.

### Function routing caveat

Cloudflare documents that `_redirects` rules do not apply to requests handled by Pages Functions. If Functions are added, route exclusions or equivalent redirect logic must be implemented and tested in the Function path.

### Host redirects

The `_redirects` file does not provide the full domain-level redirect behavior needed for every host case. Use Cloudflare Redirect Rules, Bulk Redirects, or another host-aware edge rule for:

- `www` to apex or apex to `www`;
- production `pages.dev` host to the canonical domain (Bulk Redirects, see section 17); and
- HTTP-to-HTTPS behavior not already enforced by the platform.


### Baseline header set

The following is a starting point, not a copy-and-deploy final policy:

```text
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(), microphone=(), geolocation=()
  X-Frame-Options: DENY

/_next/static/*
  Cache-Control: public, max-age=31536000, immutable

https://ultimate-fleet-gps-site.pages.dev/*
  X-Robots-Tag: noindex, nofollow
```

### Required review before production

- replace the project hostname with the actual assigned hostname;
- verify branch and deployment preview host coverage;
- confirm whether embedded ATS or approved third-party pages require framing exceptions;
- validate `Permissions-Policy` against actual features;
- add HSTS only after HTTPS and subdomain implications are approved;
- design and test Content Security Policy against actual analytics, Turnstile, fonts, images, forms, and integrations;
- confirm cache rules do not apply to mutable HTML or sensitive responses; and
- test headers on canonical, alternate, preview, asset, and error URLs.

### Function-response caveat

Cloudflare documents that `_headers` rules do not apply to responses generated by Pages Functions. Any Function must set its own security, privacy, CORS, cache, and robots headers.

## 25. Content Security Policy Rollout

### Phase 1: dependency inventory

List every required origin for:

- first-party scripts and styles;
- GA4 or tag management;
- Cloudflare Turnstile;
- form endpoint;
- fonts;
- images;
- embedded ATS content;
- consent tooling;
- monitoring; and
- approved media.

### Phase 2: report-only policy

Deploy a reviewed `Content-Security-Policy-Report-Only` policy when a report collector and privacy review exist. Observe violations from real templates and forms.

### Phase 3: enforcement

Remove unnecessary origins and enforce the narrowest working policy.

### CSP rules

- avoid `*` sources;
- avoid `unsafe-eval`;
- minimize or eliminate `unsafe-inline` through framework-compatible nonces, hashes, or validated static behavior where feasible;
- set `object-src 'none'` unless a verified feature requires otherwise;
- set `base-uri 'self'`;
- use `frame-ancestors` for framing control;
- scope `connect-src` to approved analytics and form endpoints;
- test Turnstile and consent flows; and
- update CSP through reviewed code whenever a vendor changes.

Do not deploy a strict CSP blindly and break applications, consent, or analytics on launch day.

## 26. HSTS Strategy

### Prerequisites

Before enabling HSTS:

- canonical domain serves valid HTTPS;
- alternate host redirects over HTTPS;
- all required first-party subdomains support HTTPS;
- no legacy service depends on HTTP;
- certificate renewal is understood; and
- business and technical owners approve the recovery implications.

### Rollout

1. Start with a short `max-age`.
2. Monitor domain and subdomain behavior.
3. Increase the duration after confidence is established.
4. Add `includeSubDomains` only after every relevant subdomain is verified.
5. Consider preload only as a separate high-impact decision.

HSTS mistakes persist in browsers until the directive expires. Treat long durations and preload as deliberate security changes, not default launch settings.

## 27. Cache Strategy

### Hashed framework assets

Use long-lived immutable caching for fingerprinted assets such as `/_next/static/*`.

### Images and fonts

Use long-lived public caching when filenames are stable or versioned and the asset replacement process is understood.

### HTML

Use Cloudflare Pages defaults unless measured behavior supports a custom policy. HTML must update promptly after a deployment, especially for active and closed jobs.

### Search files

Sitemaps and robots files must refresh with deployments. Do not apply an immutable one-year policy.

### Form and API responses

Sensitive, user-specific, and form-submission responses require explicit no-store behavior in the backend.

### Query-string and cache rules

Do not create broad cache rules that vary on or ignore unknown query strings without testing campaign attribution, preview tools, and form behavior.

### Purges

- rely on atomic Pages deployments for ordinary releases;
- use purge only for verified stale content or incidents;
- avoid broad purge operations without a clear target and validation plan; and
- record manual purge actions during incidents.

## 39. Rollback Strategy

### Rollback triggers

Rollback may be appropriate when a release causes:

- site-wide outage;
- broken priority navigation;
- inaccessible or unusable applications;
- applications sent to the wrong system;
- false active or closed job status;
- exposed secret or private data;
- severe metadata, canonical, robots, sitemap, or schema failure;
- widespread broken assets;
- destructive redirect loop;
- production analytics contamination that cannot be isolated quickly; or
- material legal or business inaccuracy.

### Cloudflare rollback

Cloudflare Pages supports rolling production back to a previous successful production deployment through the deployment interface, subject to current platform behavior.

### Rollback procedure

1. Confirm the incident and affected scope.
2. Stop further releases.
3. Identify the last known good production deployment and commit.
4. Roll back through Cloudflare if this safely restores service.
5. Verify the canonical domain, priority routes, forms, headers, redirects, and analytics.
6. Correct or revert the repository so Git matches the intended production state.
7. Deploy the repository-backed fix.
8. verify downstream ATS/CRM and candidate data handling.
9. Notify required business and technical owners.
10. Record the incident, impact, timeline, and preventive action.

### Important limitation

A deployment rollback may not reverse:

- DNS changes;
- Cloudflare zone-level Redirect Rules;
- nameserver changes;
- external ATS/CRM records;
- sent emails or SMS;
- environment-variable changes;
- Worker deployments;
- third-party profile updates; or
- search engine crawling.

Each external change requires its own rollback step.

## 40. DNS Rollback

### Requirements

- Preserve the previous DNS values before cutover.
- Keep the previous host available for the approved observation period.
- Know whether the prior certificate and origin remain valid.
- Avoid simultaneous unrelated DNS changes.
- Define who can authorize rollback.

### Procedure

1. Confirm the problem is caused by DNS or the new origin.
2. Restore the explicit validated previous record values.
3. Confirm resolution from multiple recursive resolvers or networks.
4. Verify the old origin and certificate.
5. Confirm email and other records remain intact.
6. Keep the new deployment available for diagnosis without public routing.
7. Record exact changes and propagation behavior.

DNS rollback is not instantaneous because recursive resolvers may retain earlier answers until TTL expiration.

## 42. Incident Playbooks

### Failed production build

- confirm old production remains available;
- inspect the first fatal error;
- reproduce with the same Node version and lockfile;
- fix through Git;
- rerun required checks; and
- redeploy.

### Form outage

- confirm site availability separately;
- test backend health and Turnstile;
- stop false success confirmations;
- display the approved fallback contact method if needed;
- alert recruiting or commercial owner;
- reconcile missed or queued submissions; and
- verify before closing the incident.

### Wrong job published

- disable the application path;
- remove job schema and sitemap entry;
- deploy the corrected job registry;
- update recruitment platforms;
- review received applications and communications; and
- document the source-of-truth failure.

### Preview indexed

- add or repair `X-Robots-Tag`;
- remove public links;
- restrict access where appropriate;
- use applicable search removal tools only as a temporary visibility measure;
- preserve production canonicals; and
- audit all preview host patterns.

### Secret exposure

- revoke and rotate immediately;
- inspect access and logs;
- remove the secret from current files and Git history through an approved process where necessary;
- redeploy affected services;
- assess applicant/customer impact;
- notify required parties; and
- add prevention controls.
